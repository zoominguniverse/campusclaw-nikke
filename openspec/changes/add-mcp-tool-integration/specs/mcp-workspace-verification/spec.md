# Spec Delta

## Purpose

把 MCP 配置、调用反馈和可复现验证融入现有教学工作区，让教师能独立完成登记到绑定，让学生能辨认工具使用状态。通过与处理器同源的文档、隔离接口报告和课堂复核证据，证明实际链路成立而非仅有界面或宿主模拟。

## ADDED Requirements

### Requirement: Teacher workspace supports the complete management flow
The existing teacher configuration workspace SHALL provide server registration, editing, connection, disconnection, deletion, discovered-tool inspection and recent audit browsing. It SHALL display connection failures independently from agent and skill management. Full descriptions and input schemas SHALL be inspectable before confirming a binding.

#### Scenario: Teacher configures a teaching tool
- **WHEN** a teacher registers the Compose MCP URL, connects, reviews declarations and saves a skill reference
- **THEN** the actual discovered names are visible and the skill becomes available for agent binding without manually editing a database

#### Scenario: MCP list request fails
- **WHEN** MCP management cannot load
- **THEN** the page reports that error while existing agent and skill configuration remains usable

### Requirement: Conversation UI presents tool outcomes accessibly
The tutor workspace SHALL display per-turn tool references, round and status before answer text, recover them from history and handle repeated metadata without duplicate messages. Desktop, narrow-screen and keyboard flows SHALL remain usable. Students SHALL have no MCP management controls.

#### Scenario: Tool denied during a stream
- **WHEN** metadata reports a denied tool followed by a normal answer
- **THEN** the UI displays the refusal clearly and continues rendering deltas in the same assistant message

### Requirement: Handler annotations generate MCP API documentation
The existing OpenAPI generator SHALL document all MCP management operations and updated skill confirmation, audit and SSE contracts from handler annotations. Swagger SHALL support same-origin Bearer trials of registration, connect, discovered tools and skill save. Token request fields SHALL be write-only with placeholder examples and absent from response schemas.

#### Scenario: Documentation matches routing
- **WHEN** generated operations are compared with the running application
- **THEN** paths, methods, roles, status codes and tool metadata agree, and no separate handwritten endpoint registry is required

### Requirement: Isolated API verification exercises real MCP traffic
`apitest/` SHALL cover registration, updates, connection, discovered tools, disconnection, deletion, role denial and class isolation. At least one end-to-end case SHALL connect the actual custom service, bind a discovered tool, obtain model-requested execution through a conversation and assert an `ok` audit row. Reports SHALL be generated by `run_all.py` and excluded from Git.

#### Scenario: Deterministic multi-round verification
- **WHEN** the isolated model fixture requests tools in two rounds over HTTP
- **THEN** real `tools/call` traffic, SSE order, stored messages and audit records agree for both rounds

#### Scenario: Wrong destination for test runner
- **WHEN** verification is pointed at the existing development deployment or database
- **THEN** preflight refuses execution before creating test records

### Requirement: Acceptance distinguishes automated evidence from human review
Acceptance records SHALL include standalone health, auth, discovery and call results; host connect-to-audit success; disconnect refusal; secret-boundary checks; real-model tool choice and guidance review; and the four course peer checks. Fixture success SHALL NOT count as real-model or actual peer review. Peer checks without actual completion and user confirmation SHALL remain pending.

#### Scenario: Automated suite passes but actual peer review is absent
- **WHEN** all automated checks pass without actual peer review and user confirmation
- **THEN** the acceptance record keeps peer checks open rather than claiming full course acceptance

### Requirement: User confirmation accepts completed actual peer checks
Actual peer checks SHALL be accepted when the user explicitly confirms that a real peer completed all four checks and the results are correct. The acceptance record SHALL retain the confirmation date and conclusion. Peer names, screenshots and raw request/response files MAY be retained as optional supporting material and SHALL NOT be prerequisites for completion.

#### Scenario: User confirms completed actual peer checks
- **WHEN** the user explicitly confirms that a real peer completed server/tool isolation, token non-disclosure, disconnect refusal and audit scope isolation and that the results are correct
- **THEN** the acceptance record records the confirmation date and conclusion and marks peer verification complete without requiring peer names, screenshots or raw request/response files

### Requirement: Existing lesson behavior remains regression checked
MCP verification SHALL retain the existing opaque Bearer lifecycle, class and subject isolation, material/index workflows, private conversation ownership, citation filtering and no-MCP streaming checks. It SHALL NOT mark unfinished earlier changes complete or require resetting development data.

#### Scenario: Existing skill without MCP
- **WHEN** a learner uses a preexisting knowledge-only skill after upgrade
- **THEN** its retrieval, citation, history and incremental answer contracts still pass their established checks
